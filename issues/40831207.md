## 내용

`sql::Database`의 수동 트랜잭션 API(`BeginTransactionDeprecated()` 등)를 없애고 RAII
`sql::Transaction`으로 통일. 남은 호출처는 전부 "장수(long-running) 트랜잭션" 패턴
(열 때 BEGIN → 쓰기 배치 → 타이머 주기 커밋+재BEGIN → 닫을 때 커밋; fsync 비용 절약):

| 대상 | 상태 |
|---|---|
| `storage/browser/quota/quota_database.{h,cc}` | CL A = CL 8282239, 리뷰 1라운드 반영 + ToT 리베이스 (+46/−6, 3파일) |
| `components/favicon/core/favicon_database` + `favicon_backend.cc` | CL B 예정 (호출처 5곳, 한 파일) |
| `components/webdata/common/web_database.cc` | **안 건드림** — `use_scoped_transaction_` 플래그로 타인 이행 중 |
| `sql/database.h` Deprecated 메서드 3개 삭제 | CL C (web_database 정리 후, `Fixed:` 는 여기서만) |

## CL A 최종 설계 (quota)

- `std::optional<sql::Transaction> transaction_` 멤버 (`db_` 뒤 선언 = 먼저 파괴).
  optional인 이유: `sql::Transaction`은 `Begin`/`Commit` 각 1회만 가능한 일회용 →
  주기 커밋마다 `emplace`로 재생성해야 함
- **`RecoverOrRaze()`**: `sql::Recovery`에 넘기기 전에 `transaction_.reset()` (리뷰 지적 ①)
- **`Commit()`**: `if (transaction_) Commit()` → `CHECK(!HasActiveTransactions())` → `emplace` →
  `if (!Begin()) { TODO; reset(); }` — **2라운드에서 Evan이 CHECK(Begin)을 거부**(I/O 에러로 크래시 불가)해 최종 확정.
  reset()은 sql::Transaction이 일회용·이동불가라 필요한 부품(크로미움 선례: net/disk_cache/sql, segmentation_platform)
- **`EnsureOpened()`**: `Begin()` 실패를 `kDatabaseError`로 보고(리뷰 지적 ③) +
  `db_`/`meta_table_` 리셋 + `is_disabled_` — 위 두 형제 실패 경로와 동일한 종착 상태
- **테스트 추가**: `LongRunningTransactionIsReopenedAfterCommit` — 지운 CHECK가 지키던 불변식을 대체

## 리뷰 1라운드 (evanstade@, nit 3건) 와 그 뒤에 일어난 일

지적 자체는 작았지만(라인 이동 / CHECK 삭제 / 주석 삭제+에러 반환), 반영하는 과정에서
**내가 두 번 판단을 바꿨다.** 기록해 둘 가치가 있는 부분.

**1차 오판 — "일관성을 맞추자".** 리뷰어가 ③에서 "트랜잭션 없이 조용히 진행한 건 실수였던 것 같다"고
했으니 그 논리를 `Commit()`에도 적용해야 한다고 판단하고, 재-`Begin()` 실패 시 DB를 통째로 비활성화하도록
바꿨다. 사용자가 "트랜잭션 관련 코드 전체를 읽고 다시 판단하라"고 해서 전부 읽은 뒤 **되돌렸다.**
두 상황이 대칭이 아니었기 때문:

| | `EnsureOpened()` | `Commit()` |
|---|---|---|
| 실패의 의미 | DB를 못 씀 | 배치만 깨짐 (autocommit으로 데이터는 정상 저장) |
| 에러 통로 | `QuotaError` 반환 | `void` |
| `db_.reset()` 안전성 | 여는 중이라 statement 없음 | 호출자가 live `sql::Statement`를 들고 있을 수 있음 → `sql/database.cc:638`이 API 위반으로 규정 |

**2차 오판 — "원본 동작을 보존했다".** 되돌리면서 "원본은 조용히 no-op이었다"를 근거로 삼았는데,
감사에서 **틀린 것으로 드러났다.** origin/main의 `Commit()`은
`CHECK_EQ(1, db_->transaction_nesting(), base::NotFatalUntil::M148)`로 시작하고,
`base/check.h`가 "`NotFatalUntil::M120`은 M120부터 크래시한다"고 명시하며 `chrome/VERSION`은 **154**다.
즉 **원본은 BEGIN 실패 시 크래시했다.** 이 CL은 그 크래시 경로 두 개를 없애는 셈이라 방향은 맞았지만,
내가 댄 근거는 사실이 아니었다.

**감사가 실제로 바꾼 것** (major 5건은 적대적 검증에서 전원 반박, minor/nit에서 건짐):

- `Commit()` 가드 확장(`!db_ || !transaction_`)을 **원복** → 요청 없던 변경 제거, diff 축소
- 대신 자가 치유 형태로 재작성 (`if (transaction_) Commit(); emplace; Begin()`) → 일시적 실패에서 복구,
  `timer_.Stop()` 스킵 버그도 동시 해결
- **헤더 주석이 거짓이었음** — "Kept open whenever `db_` is open"이 이 CL 자신이 깨는 불변식이었다.
  **리뷰어가 ③에서 지적한 바로 그 유형의 주석을 내가 새로 만들고 있었던 것.** 수정함
- 회귀 테스트 추가 + 변이 테스트로 검증 (재-`Begin()` 제거 시 `/0`,`/1` 둘 다 FAILED → 원복하면 통과)
- `is_disabled_` 논란은 무의미로 판명: `QuotaManagerImpl`이 에러 반환만으로 이미 세션을 영구 비활성화함
  (`quota_manager_impl.cc:1865, 2727`, 되돌리는 코드 없음)

**교훈:** 리뷰 지적을 반영할 때 "저 원칙을 여기에도 적용해야 하나"는 **적용 전에 두 상황이 정말 같은지부터
확인할 것.** 그리고 "원본 동작을 보존했다"고 말하려면 원본을 **실제로 읽어야** 한다 —
`NotFatalUntil` 같은 milestone 인자는 지금 버전 기준으로 이미 만료됐을 수 있다.

## ToT 리베이스 (2026-08-27) — 업스트림이 같은 줄을 먼저 고침

Gerrit에 merge conflict 표시 → 원인은 **crrev.com/c/8281077** (JP Gravel, 2026-08-26 머지,
"Remove use of deprecated transaction_nesting in QuotaDatabase"). Evan의 리뷰 다음 날 랜딩됐고
우리가 건드린 CHECK들을 정확히 다시 씀:

```cpp
db_->CommitTransactionDeprecated();
CHECK(!db_->HasActiveTransactions(), base::NotFatalUntil::M148);
CHECK(db_->BeginTransactionDeprecated(), base::NotFatalUntil::M148);   // Begin 성공 단언은 남김
```

그의 CL 설명 논리는 Evan 지적과 동일("nesting CHECK_EQ는 QuotaDatabase 불변식이 아니라 Database
내부 구현 검증")이지만, **Begin 성공 단언 하나는 의도적으로 보존**. 하루 전 랜딩한 단언을 조용히 지우면
남의 CL을 되돌리는 셈이라 새 API로 번역해 이어받음 → 그 결과 내가 고민하던 "저하 vs 비활성화" 논쟁은
팀이 이미 CHECK로 답을 정한 것으로 종결.

- 테스트 헬퍼도 `GetTransactionNesting` → `IsGlobalTransactionValid`로 바뀌어 새 테스트 수정
- `EnsureOpened()`는 업스트림이 안 건드림(여전히 Begin 반환값 무시) → Evan 요청(에러 반환) 유지
- gclient sync + 재빌드(19,705스텝, 2h22m) 후 **QuotaDatabase 59/59, quota 전체 308/308 통과.**
  그동안 크래시하던 `Incognito_Static_FlagEnabled`도 이번엔 통과(배치 순서 변화로 추정)
- 교훈: "CQ가 REBASE_ALWAYS라 리베이스 생략 가능"은 **충돌이 없을 때만**. 5일 묵히면 겹친다.
