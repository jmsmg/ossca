# [<crbug>] <이슈 제목 — 무엇을 어떻게 바꾸는가>

**상태: <지금 어디 — 예: 코드 진단 중 / CL <번호> 업로드(날짜), 리뷰 대기 / ✅ 머지(날짜)>**

> 한 이슈가 8단계를 통과하며 남기는 기록. 단계 파일(STATUS)이 "지금 어디"라면 이 파일은 **"왜 그렇게"**.
> 판단이 바뀌면(리뷰로 뒤집힌 전제, 오판) 지우지 말고 아래 «리뷰 라운드» 절에 남긴다.
> 채워진 예시: [`../examples/issues/`](../examples/issues/) — 오판→방향 전환은 `443042812.md`, CL 시리즈는 `40831207.md`, 스펙 대조·TDD는 `545843242.md`
> 이 파일을 `issues/<crbug>.md`로 복사한 뒤 이 인용 블록은 지운다.

## 링크

- crbug: https://crbug.com/<crbug> (등록 연도 · 마지막 활동 · 연결 CL 수 · 미할당 여부 → 휴면/활성 판정)
- 발굴 경로: 1단계 GUIDE 경로 <n> (<어떻게 찾았나>)
- OSSCA 이슈: #<번호> (등록 날짜) — 미등록이면 문안 `steps/2-ossca-issue/drafts/<crbug>.md`
- Gerrit CL: https://crrev.com/c/<CL번호>
- 기여 기록 PR: <contributions repo PR 링크>

## 이슈 실체

이슈 설명을 그대로 믿지 말고 **코드를 열어 재진단**한 결과를 적는다.

- 어떤 코드가 무슨 일을 하는데, 어디가 어떻게 어긋나 있는가 (`파일경로::함수()` 단위)
- 근거: 스펙 조항 / 헤더 주석 / TODO 원문 / 크래시 리포트 / blocking 체인 — **인용**으로
- 호출처: `git grep` 결과 (착수 전 5분 — 3단계 GUIDE)
- 시리즈인가: 한 crbug에 작업이 여럿이면 CL A → B → C로 나누고 순서를 적는다

## 설계 / 수정 계획

- 수정 파일, 바꾸는 방식, **범위 밖으로 남기는 것과 그 이유**
- 컨벤션 확인: 목적지 파일의 정렬 규칙 · 그 모듈의 관용구 · BUILD.gn 의존성
- 예상 diff 크기 (Gerrit 뱃지: XS <10 · S 10–49 · M 50–249 · L 250–999)

## 검증 (TDD)

- [ ] 회귀 테스트 먼저 → 수정 전 **실패** 확인 (버그 재현 증거)
- [ ] 수정 → 통과 (`<타깃> --gtest_filter='<필터>'` N/N)
- [ ] (불변식을 지키는 테스트면) 변이 테스트 — 지키려는 코드를 빼면 실패하는가
- 러너: `$OSSCA/steps/4-build-and-test/scripts/run.sh <이름> <타깃> '<필터>'` → 로그 `logs/<이름>_*.log`

## 리뷰어 근거

- 해당 디렉토리 `OWNERS` ∩ 최근 활동자 (`git log --format='%an %ae' -10 -- <파일>`)
- 팀 알리아스가 있으면 그것 (예: payments는 `chrome-payments-reviews@google.com`)
- 멘토(`$MENTOR_EMAIL`): docs 폴더면 리뷰어에, 그 외 폴더면 CC에

## 커밋 메시지 초안

```
[<모듈>] <현재형 동사로 시작하는 제목, 마침표 없이>

<왜 바꾸는지, 기존 동작이 무엇이었고 무엇이 달라지는지. 시리즈면 그 맥락. 72자 줄바꿈>

Fixed: <crbug>      ← 이 CL로 이슈가 끝나면.  시리즈 일부·부수 항목이면  Bug: <crbug>
```

## 진행 체크리스트

- [ ] 1 발굴 + triage (선점 CL 0 / OSSCA 겹침 0 / 마지막 활동) + 코드 진단
- [ ] 2 OSSCA 이슈 등록 + self-assign (또는 클레임 / 의사 타진 댓글 — 2단계 GUIDE 표)
- [ ] 3 브랜치 `<설명>-<crbug>` + 회귀 테스트(빨강) + 수정(초록)
- [ ] 4 빌드·테스트 로그 (`logs/`), 실패 0
- [ ] 5 AI 흔적 검사 → `git cl upload` (본인 직접) → `track.py verify <CL> <PS>` 서버=로컬 ✓
- [ ] 6 리뷰 라운드 … MERGED (날짜 · 커밋 해시 · 최종 PS)
- [ ] 7 기여 기록 `data/contributions/<CL>.md` + PR (`status: in review`) — **업로드 직후 6과 병행**
- [ ] 8 마무리: 기록 `status: merged` PR / OSSCA Status `반영 완료` / 이 파일 마감 / `BOARD.md` 갱신

## 리뷰 라운드 — 바뀐 판단

라운드마다: 지적 요지 → **직접 코드를 읽어 독립 검증**한 결과 → 반영 / 반박 → 새 PS.
내 전제가 틀렸으면 무엇을 왜 잘못 봤는지 그대로 남긴다 (예시: `443042812.md`의 «처음 판단» 절).
