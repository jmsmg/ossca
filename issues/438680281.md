## 이슈 실체

`NotFatalUntil`은 **새 CHECK를 단계적으로 켜는 장치**다. `CHECK(cond, NotFatalUntil::M143)`은 M143 전까지는
죽지 않고 덤프만 남기고, M143부터 fatal이 된다 — 그동안 크래시 리포트로 "켜도 되는지"를 탐색하라는 것.

판정은 `base/check.cc:69`:

```cpp
LogSeverity GetNotFatalUntilSeverity(base::NotFatalUntil fatal_milestone) {
  if (... std::to_underlying(fatal_milestone) <= BASE_CHECK_VERSION_INTERNAL) {
    return LOGGING_FATAL;
  }
  return GetDumpSeverity();
}
```

현재 MAJOR=155, 143 ≤ 155 → **이미 12개 마일스톤째 fatal**. 인자는 효과 없이 남아 있는 잔여물이다.
그리고 정리 방법을 헤더가 직접 지시한다 (`base/not_fatal_until.h:14`):

> To clean up old entries remove the already-fatal argument from CHECKs **as well as from this list**.
> This generates better-optimized CHECKs in official builds.

즉 이건 개선 제안이 아니라 **원래 롤아웃 계획의 마지막 단계**다. 40831207("deprecated and will be removed"
헤더가 정리를 지시)과 같은 유형이라 클레임 없이 직행할 수 있다.

  아직 검사 없음)이 남아 있으므로 `Fixed:` 아님

## 동작 변화 — 정직하게 적어야 할 것

크래시 여부는 **안 바뀐다**(이미 fatal). 바뀌는 건 코드 생성이다. `base/check.h:260`:

> Discard log strings to reduce code bloat when there is no NotFatalUntil argument
> (which temporarily preserves logging both locally and in crash reports).

인자가 있으면 공식 빌드에서도 로그 문자열이 보존돼 크래시 리포트에 올라간다. 빼면 **공식 빌드에서 `<< path`가
버려진다** — 바이너리가 작아지는 대신 이 CHECK가 터졌을 때 어떤 pref였는지 리포트에서 안 보인다.
헤더가 말하는 "better-optimized"의 실체가 이 트레이드오프이므로 CL 설명에 명시했다.
