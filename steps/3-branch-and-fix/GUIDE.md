## 브랜치

```bash
cd ~/chromium/src
git new-branch <설명>-<crbug번호>     # 예: spc-delegate-guard-443042812
```

- **브랜치 하나 = CL 하나.** main에서 직접 커밋 금지
- 최신 main 반영: `git fetch origin && git rebase origin/main && gclient sync`
- 빌드 트리와 base를 맞추려 옛 커밋에서 브랜치를 딴 경우, **업로드 전에 반드시 리베이스**
  (40681786이 8/26 base에서 작업 → 업로드 전 리베이스)

## 착수 전 5분: 호출처를 직접 따라간다

**443042812에서 가장 비싸게 배운 것.** "delegate가 파괴될 수 있다"는 가설로 가드 + 회귀 테스트를
만들고 15시간 43분 풀빌드까지 돌렸는데, 리뷰어가 호출처 분석 한 번으로 전제를 무너뜨렸다.
`Create()`의 호출처를 `git grep` 한 번만 했어도 5분 안에 알 수 있었다.

착수 전 필수:

```bash
git grep -n '함수명' -- <디렉토리>      # 호출처 전부
git log -L :함수명:<파일>              # 그 함수가 언제 왜 이렇게 됐는지
```

가짜 근거로 자주 쓰이는 것 두 가지 — 둘 다 443042812에서 실제로 속은 것:

1. **같은 파일의 다른 가드**: 비동기 콜백의 생존 가드는 *비동기 경로*에 대한 증거일 뿐,
   동기 진입부에는 적용되지 않는다. 같은 파일이라는 이유로 일반화하지 말 것
2. **크래시 리포트의 스택**: 무관한 프레임이 붙어 있으면 스택이 깨져 시그니처가 오귀속된 것.
   리포트를 근거로 쓸 거면 스택 자체의 정합성부터 검증

## TDD 순서

1. **회귀 테스트 먼저** 작성
2. 수정 전에 실제로 **실패하는 것 확인** (= 버그 재현 증거)
3. 수정
4. 통과 확인

- 테스트가 불변식을 정말 지키는지 의심되면 **변이 테스트**: 지키려는 코드를 일부러 빼고
  테스트가 실패하는지 확인 (8282239에서 사용, 러너 `~/ossca/steps/4-build-and-test/scripts/mutation_test.sh`)
- test fixture의 헬퍼가 `EXPECT_CALL` 기대를 거는 경우 주의 — 미충족 기대로 오탐 가능
- 동작 불변 리팩토링이면 기존 테스트 전원 통과가 곧 검증 (40681786)

## 범위 결정 — 시리즈로 쪼개기

한 crbug에 TODO/작업이 여러 개 걸려 있으면 **CL 시리즈**로 나눈다. 리뷰 단위를 작게 유지하고
앞 CL이 머지돼야 뒤 CL이 성립하는 순서를 만든다.

- 40831207: CL A(quota) → CL B(favicon) → CL C(sql 메서드 삭제)
- 40681786: 에러 문자열 이동(1/3) → 나머지 TODO

**범위 밖은 명시적으로 남긴다.** 이슈 문구가 "error message"만 말하면 `log.Warn()` 13곳은 건드리지
않고, 그 판단을 CL 설명이나 `issues/<crbug>.md`에 적는다. 리뷰어가 원하면 후속 CL.

## 컨벤션 확인

수정 대상 디렉토리의 기존 패턴을 먼저 읽는다 — 그게 곧 리뷰 통과 조건이다.

- 목적지 파일의 정렬 규칙(엄격한 알파벳순인지, 기능별 그룹인지)
- 그 모듈이 이미 쓰는 관용구 (`$N` 플레이스홀더 + `ReplaceStringPlaceholders` vs `StringPrintf`)
- `-Wformat-nonliteral` 처럼 컨벤션을 강제하는 컴파일러 경고
- BUILD.gn 의존성이 이미 있는지 (`//components/payments/core` 등)
